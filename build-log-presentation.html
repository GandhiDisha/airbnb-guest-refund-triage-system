The assignment

The same complaint can be three different stories.

"AC broken" can be a genuine, evidenced, in-stay-reported issue — or an unreported non-issue surfacing only at checkout — or an opportunistic claim. An agent has seconds to tell those apart, and getting it wrong in either direction has a real cost: over-refund erodes host trust and revenue, under-refund erodes guest trust and retention.

The tool doesn't decide — it triages. It reads the reservation, the chat log, the listing, and both parties' history, then hands the agent a recommended decision, an amount, and a draft response to review and send. The agent keeps the pen the whole time.

"Nothing in the problem statement specifies how booking value, nights, issue category, and severity combine into a refund percentage. Airbnb's own AirCover policy is itself not formulaic — it's explicitly case-by-case." product-brief.md · §3, hidden requirement 5

PHASE 1 · BUILD & SHIP

Make it real before making it right.

A working product first — deployed, usable, and honest about its own uncertainty — before any claim about quality.

Core

Deterministic decision engine + LLM narration

The refund percentage is computed from structured signals, deliberately not an LLM call — so it's consistent and testable run-to-run. A separate narration layer explains the fixed decision; it never re-derives it.

Data

Mock/Supabase parity fix

Local fixtures had drifted from the seed data, including a real scoring bug in the host-accountability multiplier — caught by comparing the two sources line for line, not by guessing.

UX

Booking-ID search, not memorization

Raw UUIDs were "difficult to remember" for agents — replaced the text field with a searchable combobox instead of just shortening the ID.

Transparency

Model picker with live cost/token display

Agents choose which Claude model narrates a complaint (Haiku 4.5 / Sonnet 5 / Opus 5) and see the real input/output token count and estimated cost per analysis — no black box.

PHASE 2 · INSTRUMENT

You can't improve what you haven't measured.

Before touching the engine again, build a way to know — objectively, repeatably — whether a change made it better or worse.

The golden set

  • 27 hand-labeled cases, expert-adjudicated ground truth
  • All 5 issue categories × the full legitimacy spectrum
  • 1 demographic-coded bias-audit pair, identical facts
  • 4 cases re-run 3× each to measure run-to-run consistency

The rubric — 8 dimensions

  • 5 programmatic: decision, amount, safety recall, consistency, bias delta
  • 3 Opus-judged: groundedness, tone & liability, explainability
  • Judge is given the case + output — never the golden answer
  • Opus-5 fixed as judge, independent of which model narrates
"The judge must never be more permissive than the system it's grading — using a top-tier model as judge keeps that invariant true even as the app's own model choice changes." eval-criteria.md · judge model rationale

Field notes

Seven catches worth remembering.

01

The dataset had the bug, not the engine

8 of 27 golden cases had single-message chat logs, making "was this raised in-stay or at checkout" mathematically undecidable. The eval doesn't just grade the tool — it has to be graded itself.

02

The RAG that turned out not to be needed PM hypothesis, tested

The working theory was "we probably need retrieval to synthesize chat evidence." Checking the actual token footprint first (every case fits in ~500–2,000 tokens — nothing to retrieve) surfaced two real prompt bugs instead of a speculative rebuild.

03

"That's normal" isn't the same as "that's fine"

Matching and timing were both already correct — the engine just couldn't tell a host confirming a real problem from a host explaining it away as expected behavior. Same evidence boost either way, until a phrase check on the host's reply fixed it.

04

A curly quote broke a keyword match

"isn't working" (straight apostrophe) never matched "isn't working" (curly apostrophe) in the actual chat text. String heuristics are only as reliable as the character set they assume.

05

A bonus every other category got, on principle — not on a raw count PM catch

Host Responsiveness was structurally locked out of the same evidence bonus every other category earned, since "no reply" can't corroborate the way a host's reply does. The fix couldn't just count any unanswered message either — it had to be a real question or complaint, not a check-in "here" or "leaving," or it would've rewarded noise instead of signal.

06

Whose evidence is it, really? PM catch

A case leaned on a different guest's past review as corroboration, while the current guest offered no photo of their own. Reading a public review isn't the same as proving your own claim — that distinction now lowers confidence and routes the case to manual review.

07

The spec had already answered the question

The written brief called Safety/Security "escalation-first, not primarily a refund-pct case" — but the code weighted it highest of all five categories. Re-reading the spec, not just the golden numbers, was the actual fix.

For a PM, not just an engineer

What this exercise actually teaches.

01

Eval-driven beats vibe-checking

A golden set plus a judge turns "this feels right" into a number you can re-run after every change and defend to a stakeholder.

02

Fix the judge, vary the system

Opus-5 stayed the constant referee across every run, regardless of which model narrated — so a score change could only mean the product changed.

03

Write the spec before the code

The brief's "escalation-first" framing for Safety wasn't front of mind at build time — but it settled a real calibration debate six days later.

04

Bugs hide at every layer

Dataset authoring, prompt wording, character encoding, and formula calibration each produced a real, measurable miss — not just "the code."

05

Test the hypothesis before building it

"We probably need RAG" was a reasonable guess. Checking the actual token footprint first saved building infrastructure the problem didn't need.

06

Confidence is a feature

Teaching the tool to say "route this to a human" on genuinely ambiguous cases mattered as much as getting the confident cases right.

07

Small, verified steps compound

44% → 100% decision accuracy came from nine narrow, independently re-checked changes against all 27 cases — not one rewrite.

08

Domain judgment is still the PM's job

Two of the sharpest fixes this session — treating review-only corroboration as weaker evidence, and refusing to reward Host Responsiveness's bonus on raw silence instead of a real complaint — both came from product reasoning, not from re-reading code.

Open items

What isn't finished yet — on purpose, said plainly.

Data-limited

Two remaining "disputed" golden cases don't contain a detectable signal for the uncertainty their rationale describes — the input data would need to change before a heuristic safely could.

Threshold

The groundedness release gate ("zero unsupported claims, dataset-wide") has failed every run so far — worth deciding whether that's the right bar or an overly strict one.

Uncalibrated

Host Responsiveness's base severity weight is still lower-confidence than the other four categories and hasn't been recalibrated against the golden set the same way Safety was.
